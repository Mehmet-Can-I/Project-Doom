# Snake on NUCLEO-L476RG — Project Report (draft)

## 1. Introduction

For this project we built a **Snake game** on the NUCLEO-L476RG board (STM32L476RG, Cortex-M4 at 80 MHz). It runs on the lab base-stand with the OLED expansion board and the LCD Keypad Shield. We wrote it in C in STM32CubeIDE, using the HAL drivers generated by CubeMX.

The player steers the snake with the shield's buttons. The snake moves on a 128×64 OLED screen and grows each time it eats a fruit. It also gets faster, and it dies when it hits a wall or its own body. A 16×2 LCD shows the score and the best score. The board LED blinks when the snake eats a fruit and when it dies. The game can be started, paused and restarted at any time.

We implemented the following five features from the course list:

| # | Course feature | What it does in the game | Main files |
|---|----------------|--------------------------|------------|
| 1 | OLED graphic screen | Playfield: snake, fruit, border, title and game-over screens | `ssd1306.c`, `snake.c` |
| 2 | LCD display | Score, best score, game state | `lcd_hd44780.c`, `app.c` |
| 3 | ADC | All 5 shield buttons are read through **one analog input** | `keypad.c` |
| 4 | LED | Board LED LD2 blinks when a fruit is eaten and when the snake dies | `status_led.c` |
| 5 | Interrupts | TIM6 timer interrupt paces the game; EXTI interrupt on a button pauses / restarts it | `app.c` |

Extras that are also in the code: a PWM-driven RGB LED (TIM1) and a debug log over UART (`printf`, 115200 baud).

### 1.1 Software architecture

The program is a **super-loop** with **interrupt flags**. The interrupt handlers do almost nothing: they set a flag. All the slow work (drawing, LCD writes) happens in the main loop, so no interrupt is ever blocked for milliseconds.

```
main()  ──► HAL / CubeMX init ──► App_Init() ──► while(1) App_Loop()

TIM6 ISR  (1 kHz)  ──► step_pending = 1      ┐
EXTI13 ISR (button) ──► button_pressed = 1   ├─► handled in App_Loop()
ADC keypad (polled every 10 ms)              ┘
```

| Module | Role |
|--------|------|
| `main.c` | CubeMX peripheral init (clock, ADC1, TIM1, TIM6, USART2, GPIO), calls `App_Init()` / `App_Loop()` |
| `app.c` | Game state machine (TITLE → PLAYING ⇄ PAUSED → GAME_OVER), interrupt callbacks, screen texts |
| `snake.c` | Pure game logic (movement, collisions, food, speed) and drawing into the OLED frame buffer |
| `ssd1306.c` | OLED driver (feature 1) |
| `lcd_hd44780.c` | LCD driver (feature 2) |
| `keypad.c` | Analog keypad (feature 3) |
| `status_led.c` | LD2 blink patterns (feature 4) |

The game state machine (`app.c`):

```c
typedef enum { ST_TITLE, ST_PLAYING, ST_PAUSED, ST_GAME_OVER } GameState;
```

The main loop:

```c
void App_Loop(void)
{
  const uint32_t now = HAL_GetTick();

  /* FEATURE 3: sample the analog keypad every 10 ms */
  if (now - last_key_poll_ms >= 10) {
    last_key_poll_ms = now;
    Key k = Keypad_PollEvent();
    if (k != KEY_NONE) handle_key(k);
  }

  /* FEATURE 5: blue button, flagged by the EXTI interrupt */
  if (button_pressed) {
    button_pressed = 0;
    on_select();
  }

  /* FEATURE 5: snake step, flagged by the TIM6 interrupt */
  if (step_pending && state == ST_PLAYING) {
    step_pending = 0;
    SnakeEvent e = Snake_Step();
    if (e == SNAKE_EVT_DIED) {
      on_game_over();
    } else {
      if (e == SNAKE_EVT_ATE) on_fruit_eaten();
      Snake_Draw();                       /* FEATURE 1: redraw playfield */
      ssd1306_UpdateScreen();
    }
  }

  RGB_Update(now);
  StatusLed_Update(HAL_GetTick());
}
```

### 1.2 The hardware challenge: shared pins

The OLED board and the LCD shield sit on the same Arduino connector, so **three wires are shared**:

| MCU pin | OLED signal | Also connected to |
|---------|-------------|-------------------|
| PA5 | SCLK (SPI clock) | green LED **LD2** on the Nucleo |
| PC7 | D/C (data/command) | **E** (enable) of the LCD |
| PB6 | CS (chip select) | LCD **backlight** |

Our solutions to this pin sharing come up in features 1, 2 and 4.

## 2. Feature 1 — OLED graphic screen

**Hardware:** SSD1309 controller, 128×64 pixels, SPI (PA5 = SCLK, PA7 = MOSI, PB6 = CS, PC7 = D/C). The reset pin is tied to NRST.

**Starting point:** the lab library `ssd1306.c` (from `COA-LAB-DOCUMENTATION/Wyswietlacz_OLED`). We kept its drawing functions (pixels, lines, rectangles, text). We rewrote the low-level transfer layer for three reasons.

### 2.1 Frame buffer and playfield drawing

All drawing goes into a 1 KB frame buffer in RAM (128 × 64 / 8). The game uses a 31 × 15 grid of 4×4-pixel cells inside a 1-pixel border. Each snake cell is a filled 3×3 square, and the fruit is a small "+" so it looks different from the body.

```c
/* FEATURE 1: cell (cx,cy) -> pixels. 2 px offset = 1 px border + 1 px gap */
static void draw_cell_filled(uint8_t cx, uint8_t cy)
{
  uint8_t x = (uint8_t)(2 + cx * SNAKE_CELL_PX);
  uint8_t y = (uint8_t)(2 + cy * SNAKE_CELL_PX);
  ssd1306_FillRectangle(x, y, x + 2, y + 2, White);   /* 3x3, 1px gap */
}

/* FEATURE 1: redraw the whole playfield into the frame buffer.
 * ssd1306_UpdateScreen() then only transmits the bytes that changed. */
void Snake_Draw(void)
{
  ssd1306_Fill(Black);
  ssd1306_DrawRectangle(0, 0, SSD1306_WIDTH - 1, SSD1306_HEIGHT - 1, White);

  uint16_t idx = head;
  for (uint16_t i = 0; i < length; i++) {
    draw_cell_filled(body[idx].x, body[idx].y);
    idx = (uint16_t)((idx + SNAKE_MAX_LEN - 1U) % SNAKE_MAX_LEN);
  }
  if (length < SNAKE_MAX_LEN)
    draw_food(food.x, food.y);
}
```

The snake body is stored in a **ring buffer**: moving the snake means writing one new head cell and forgetting the tail, with no copying. A second array `occupied[15][31]` answers "is this cell part of the snake?" in one step. That is used for collision detection and for placing the fruit on a free cell.

### 2.2 Bit-banged SPI (so that LD2 can be controlled)

PA5 is both the OLED clock and the LD2 LED. The hardware SPI peripheral always returns the clock to LOW between bytes, which would make it impossible to keep the LED on. So we generate the SPI signal in software (mode 0, MSB first):

```c
static void ssd1306_Transmit(const uint8_t *buffer, size_t size) {
    const uint32_t sck_rise      = SSD1306_SCK_Pin;
    const uint32_t sck_fall      = (uint32_t)SSD1306_SCK_Pin << 16;
    const uint32_t sck_after_bit = spi_idle_high ? sck_rise : sck_fall;

    while (size--) {
        uint8_t byte = *buffer++;
        for (uint8_t bit = 0; bit < 8; bit++) {
            WRITE_REG(SSD1306_SCK_Port->BSRR, sck_fall);         /* SCLK low  */
            WRITE_REG(SSD1306_MOSI_Port->BSRR,
                      (byte & 0x80U) ? SSD1306_MOSI_Pin : ((uint32_t)SSD1306_MOSI_Pin << 16));
            ssd1306_BitDelay();                                  /* set-up    */
            WRITE_REG(SSD1306_SCK_Port->BSRR, sck_rise);         /* OLED reads the bit */
            __NOP(); __NOP(); __NOP(); __NOP();                  /* tCLKH     */
            WRITE_REG(SSD1306_SCK_Port->BSRR, sck_after_bit);    /* LD2 off: low again */
            byte <<= 1;
        }
    }
    spi_clock_high = spi_idle_high;
}
```

We write the GPIO BSRR register directly, which sets or clears a pin in a single instruction. For each bit:

1. The clock goes LOW and the data bit is placed on MOSI.
2. We wait `ssd1306_BitDelay()`, 8 `NOP`s = 100 ns at 80 MHz (data set-up time).
3. The clock goes HIGH; on this rising edge the OLED reads the bit.
4. After a **short** high pulse (4 `NOP`s), the clock goes LOW again if the LED must be off. If the LED must be on, it stays HIGH.

Step 4 is explained in section 5.3: it stops LD2 from flickering at every snake step. The timings respect the SSD1309 datasheet (serial interface timing: clock low time and clock high time ≥ 50 ns, data set-up and hold ≥ 15 ns).

### 2.3 Sending only what changed

A full screen is 1024 bytes. Sending it on every move would be slow and would make LD2 and the LCD backlight flicker, because they share the clock and CS wires. So we keep a copy of the last frame sent and **transmit only the runs of columns that changed**. A snake move changes only a few bytes.

```c
void ssd1306_UpdateScreen(void) {
    if (!SSD1306_FrameValid) {   /* first time: send the whole screen */
        ssd1306_UpdateWindow(0, SSD1306_WIDTH - 1, 0, SSD1306_HEIGHT / 8 - 1,
                             SSD1306_Buffer, SSD1306_BUFFER_SIZE);
        memcpy(SSD1306_PreviousBuffer, SSD1306_Buffer, sizeof SSD1306_Buffer);
        SSD1306_FrameValid = 1;
        return;
    }
    for (uint8_t page = 0; page < SSD1306_HEIGHT / 8; page++) {
        const size_t base = (size_t)page * SSD1306_WIDTH;
        uint16_t col = 0;
        while (col < SSD1306_WIDTH) {
            /* skip unchanged columns */
            while (col < SSD1306_WIDTH &&
                   SSD1306_Buffer[base + col] == SSD1306_PreviousBuffer[base + col]) col++;
            if (col == SSD1306_WIDTH) break;
            /* find the end of the changed run */
            const uint16_t first = col;
            while (col < SSD1306_WIDTH &&
                   SSD1306_Buffer[base + col] != SSD1306_PreviousBuffer[base + col]) col++;
            const size_t count = col - first;
            ssd1306_UpdateWindow((uint8_t)first, (uint8_t)(col - 1), page, page,
                                 &SSD1306_Buffer[base + first], count);
            memcpy(&SSD1306_PreviousBuffer[base + first],
                   &SSD1306_Buffer[base + first], count);
        }
    }
}
```

`ssd1306_UpdateWindow()` sets the column and page address range with the SSD1309 commands `0x21` and `0x22`, then sends the bytes.

## 3. Feature 2 — LCD display (HD44780, 16×2)

**Hardware:** LCD Keypad Shield, HD44780 controller in **4-bit mode** (RS = PA9, E = PC7, DB4–DB7 = PB5, PB4, PB10, PA8).

**What it shows:**

| Game state | Line 1 | Line 2 |
|------------|--------|--------|
| Title | `  SNAKE  NUCLEO` | `SELECT to start` |
| Playing | `Score: 7` | `Best:  12` |
| Paused | `Score: 7` | `    PAUSED` |
| Game over | `Score:7 Best:12` | `SELECT = replay` |

### 3.1 Driver

In 4-bit mode each byte is sent as two nibbles, high nibble first. The LCD reads a nibble on the **falling edge of E**. We started from the lab driver (`LCD_Keypad.c`), but it waits about 6 ms per character, which would freeze the game. We rewrote it with microsecond delays based on the Cortex-M4 cycle counter (DWT):

```c
/* Busy-wait using the Cortex-M4 cycle counter (80 cycles = 1 us). */
static void delay_us(uint32_t us)
{
  const uint32_t start = DWT->CYCCNT;
  const uint32_t ticks = us * (SystemCoreClock / 1000000U);
  while ((DWT->CYCCNT - start) < ticks) { }
}

static void lcd_write(uint8_t rs, uint8_t value)
{
  /* Wait BEFORE writing: covers the previous instruction and also the guard
   * command sent by the last OLED update (each takes <= 37 us). */
  delay_us(50);
  HAL_GPIO_WritePin(LCD_RS_GPIO_Port, LCD_RS_Pin, rs ? GPIO_PIN_SET : GPIO_PIN_RESET);
  write4bits(value >> 4);
  write4bits(value & 0x0F);
}
```

To avoid flicker we never clear the screen during the game. `LCD_PrintLine()` overwrites a whole line and pads it with spaces:

```c
void LCD_PrintLine(uint8_t row, const char *s)
{
  LCD_SetCursor(0, row);
  uint8_t n = 0;
  while (*s && n < LCD_COLS) { lcd_data((uint8_t)*s++); n++; }
  while (n++ < LCD_COLS) lcd_data(' ');   /* pad: overwrite old text */
}
```

The score is refreshed only when it changes, i.e. when a fruit is eaten (`on_fruit_eaten()` in `app.c`):

```c
static void lcd_show_score(void)
{
  char line[24];
  snprintf(line, sizeof line, "Score: %u", Snake_GetScore());
  LCD_PrintLine(0, line);
  snprintf(line, sizeof line, "Best:  %u", best_score);
  LCD_PrintLine(1, line);
}
```

### 3.2 Sharing PC7 with the OLED

The LCD's E pin is the same wire as the OLED's D/C pin. Every time the OLED driver brings D/C from HIGH (data) back to LOW, the LCD sees a falling edge on E and **reads a nibble**. If we ignored this, the LCD would receive random commands and display garbage.

We made those edges harmless:

1. D/C idles LOW, and each OLED transfer is split into **exactly two** data bursts. That gives exactly two falling edges, which the LCD reads as one complete byte.
2. Just before each falling edge, the OLED driver calls a hook that the LCD driver implements. The hook puts the command `0x0C` (display ON, cursor OFF) on the LCD data lines. The LCD is already in that state, so the "stolen" command changes nothing.

```c
/* E is shared with the OLED D/C line, so every OLED screen update also
 * clocks one byte into the LCD. We make that byte a harmless command:
 * display ON, cursor OFF, blink OFF = 0x0C. */
#define LCD_GUARD_COMMAND  (LCD_DISPLAYCONTROL | LCD_DISPLAYON)

void ssd1306_BeforeDcFallingEdge(uint8_t edge_index)
{
  if (edge_index == 0) delay_us(50);
  HAL_GPIO_WritePin(LCD_RS_GPIO_Port, LCD_RS_Pin, GPIO_PIN_RESET);
  set_data_nibble(edge_index == 0 ? (LCD_GUARD_COMMAND >> 4) : (LCD_GUARD_COMMAND & 0x0F));
  delay_us(1);   /* set-up time before the falling edge */
}
```

On the OLED side (`ssd1306_UpdateWindow`):

```c
    const size_t half = size > 1 ? size / 2 : 1;
    /* A one-byte window wraps to the same byte, so sending it twice is
     * harmless and still gives the two edges the LCD needs. */
    ssd1306_WriteData(buffer, half);
    ssd1306_DcIdleLow(0);          /* falling edge 1 -> LCD high nibble 0x0 */
    ssd1306_WriteData(size > 1 ? buffer + half : buffer,
                      size > 1 ? size - half : 1);
    ssd1306_DcIdleLow(1);          /* falling edge 2 -> LCD low nibble 0xC */
```

The LCD is initialised **before** the OLED (`App_Init()`), so it is already in 4-bit mode when the first OLED edges arrive.

## 4. Feature 3 — ADC: the buttons as one analog signal

This feature is about **reading digital buttons through an analog input**. The LCD Keypad Shield does not give each button its own GPIO. All five buttons (RIGHT, UP, DOWN, LEFT, SELECT) share **one wire, A0**, which is connected to a **resistor ladder** (voltage divider):

```
 VCC ── R2 2 kΩ ──┬────────────────────────────── A0 (PA0 = ADC1_IN5)
                  │
          RIGHT ──┤ (short to GND)
                 330 Ω
             UP ──┤
                 620 Ω
           DOWN ──┤
                  1 kΩ
           LEFT ──┤
                 3.3 kΩ
         SELECT ──┘
```

*(From the shield schematic, `p204390-lcdkeypadshield_sch-1.pdf`.)*

Pressing a button connects one point of the ladder to GND. The voltage on A0 then comes from the divider formed by the 2 kΩ pull-up and the resistance between A0 and the pressed button:

  **V(A0) = VCC · R_below / (2 kΩ + R_below)**

| Button | R_below | Theory (12-bit, VCC = VREF) | **Measured on our board** |
|--------|---------|-----------------------------|---------------------------|
| RIGHT | 0 Ω | 0 | 0 |
| UP | 330 Ω | 580 | ~745 |
| DOWN | 950 Ω | 1319 | ~1560 |
| LEFT | 1950 Ω | 2022 | ~2200 |
| SELECT | 5250 Ω | 2965 | ~2969 |
| none | ∞ | 4095 | ~3717 |

So **one analog value tells us which button is pressed**. The measured values do not match the theory exactly: the shield's VCC is not the ADC reference voltage, and the base-stand loads the line. For that reason we did not use the thresholds from the lab demo. We **measured the real levels and placed each threshold half-way between two neighbouring levels**, which leaves the largest possible margin for noise.

### 4.1 ADC configuration (`MX_ADC1_Init`)

- ADC1, channel 5 (PA0), single-ended, **12-bit** resolution (0…4095)
- Software trigger, single conversion (no continuous mode)
- ADC clock 64 MHz / 4 = 16 MHz, sampling time 47.5 cycles. One conversion = (47.5 + 12.5) / 16 MHz ≈ **3.75 µs**
- Self-calibration at start-up: `HAL_ADCEx_Calibration_Start()`

### 4.2 Code

One conversion:

```c
uint16_t Keypad_ReadRaw(void)
{
  uint16_t value = ADC_ERROR;
  HAL_ADC_Start(kp_hadc);
  if (HAL_ADC_PollForConversion(kp_hadc, 10) == HAL_OK)
    value = (uint16_t)HAL_ADC_GetValue(kp_hadc);
  HAL_ADC_Stop(kp_hadc);
  return value;
}
```

Voltage → button, using a table of voltage bands:

```c
static const struct { uint16_t max; Key key; } key_bands[] = {
  {  400U, KEY_RIGHT  },   /* level    0 */
  { 1150U, KEY_UP     },   /* level ~ 745 */
  { 1900U, KEY_DOWN   },   /* level ~1560 */
  { 2600U, KEY_LEFT   },   /* level ~2200 */
  { 3350U, KEY_SELECT },   /* level ~2969, released ~3717 */
};

Key Keypad_ReadKey(void)
{
  const uint16_t v = Keypad_ReadRaw();
  if (v == ADC_ERROR) return KEY_NONE;

  for (unsigned i = 0; i < sizeof key_bands / sizeof key_bands[0]; i++)
    if (v < key_bands[i].max) return key_bands[i].key;

  return KEY_NONE;
}
```

### 4.3 Debouncing an analog signal

Analog buttons need one extra precaution compared with digital ones. When a button is **released**, the voltage does not jump straight back to the idle level. It slides up through the bands of the other buttons. Releasing RIGHT, for example, can briefly read as UP, DOWN, LEFT or SELECT. Without a fix, the snake would turn by itself, or the game would pause on its own (SELECT).

`Keypad_PollEvent()` runs every 10 ms and solves this in two steps:
1. A key is accepted only after **two identical readings in a row** (debounce).
2. After a press is reported, **everything is ignored until a stable "no key" reading** is seen. The voltage sliding through other bands during a release is therefore never taken as a press.

```c
Key Keypad_PollEvent(void)
{
  const Key k = Keypad_ReadKey();

  if (k != candidate) {          /* reading changed: restart counting */
    candidate  = k;
    same_count = 0;
  }
  if (same_count < DEBOUNCE_SAMPLES) same_count++;
  if (same_count < DEBOUNCE_SAMPLES) return KEY_NONE;   /* not stable yet */

  if (candidate == KEY_NONE) {   /* stable release: ready for next press */
    held_key = KEY_NONE;
    return KEY_NONE;
  }
  if (held_key != KEY_NONE)      /* this press was already reported */
    return KEY_NONE;

  held_key = candidate;          /* new press */
  return held_key;
}
```

Bonus: the ADC also seeds the random generator that places the fruits. The low bits of an ADC reading contain electrical noise, so each game is different:

```c
uint32_t seed = HAL_GetTick() ^ ((uint32_t)Keypad_ReadRaw() << 16) ^ DWT->CYCCNT;
```

```c
{
  ...
  StatusLed_Blink(200, 5000);             /* FEATURE 4: blink 5 s        */
  ...

```

### 5.1 Non-blocking blinking

The blink must not stop the game, so we cannot use `HAL_Delay()`. `StatusLed_Blink()` only records the start time. `StatusLed_Update()` runs on every main-loop pass and calculates whether the LED should be on or off from the elapsed time:

```c
void StatusLed_Update(uint32_t now_ms)
{
  if (!blinking) return;

  const uint32_t elapsed = now_ms - blink_start;
  if (elapsed >= blink_duration) {
    StatusLed_Off();                                    /* pattern finished */
  } else {
    led_set((elapsed / blink_interval) % 2U == 0);      /* on, off, on, ... */
  }
}
```

### 5.2 Driving an LED that is also an SPI clock

LD2 is on **PA5, the OLED clock**. A plain `HAL_GPIO_WritePin(PA5, …)` would create an extra clock edge, and the OLED would read a wrong bit. Because we bit-bang the SPI (see 2.2), we can choose the **idle level** of the clock instead:

- idle LOW → LD2 off
- idle HIGH → LD2 on

While the LED is on, every bit the OLED driver sends ends on its rising edge, with the clock HIGH, and the clock is left HIGH. So "LED on" is simply "do not bring the clock back down after the bit". To switch the LED on while the screen is idle, the driver sends the SSD1309 **NOP command (0xE3)**. That is a complete byte that ends HIGH, and the OLED ignores it.

```c
static void led_set(uint8_t on)            /* status_led.c */
{
  if (led_on == on) return;      /* only touch the shared wire on change */
  led_on = on;
  ssd1306_SetClockIdleHigh(on);
}

void ssd1306_SetClockIdleHigh(uint8_t high)   /* ssd1306.c */
{
    spi_idle_high = high != 0;
    if (!spi_initialized) return;
    if (!spi_idle_high) {
        ssd1306_Clock(0);                 /* LED off: just drop the clock */
    } else if (!spi_clock_high) {
        /* LED on: raise the clock with a complete byte, the SSD1309 NOP
         * command E3h, so the OLED never sees a half byte. */
        ssd1306_WriteCommand(0xE3);
    }
}

/* After a transfer SCLK is HIGH only if LD2 is on; make sure it is LOW otherwise. */
static void ssd1306_RestoreIdleClock(void) {
    if (!spi_idle_high) ssd1306_Clock(0);
}
```

### 5.3 Removing the flicker at every snake step

In a first version, LD2 flickered slightly at **every step of the snake**, even while it was supposed to be off. The cause was the shared wire. Each step redraws part of the screen, which means a few hundred SPI bits, and every bit is a clock pulse on PA5, so every pulse lit LD2 for a moment. In that version the clock stayed HIGH for most of each bit: about 35–40 CPU cycles (≈ 450–500 ns), with the loop work (shifting the byte, counting bits) done while it was HIGH. That was enough light to see.

We could not remove the pulses, since the OLED needs them, but we made them as short as the OLED allows:

- the clock is brought back LOW right after the rising edge, as soon as the minimum high time (tCLKH = 50 ns) has passed;
- all the loop work is now done while the clock is LOW.

In the compiled code the HIGH pulse is now about 8 cycles (≈ 100 ns) instead of ≈ 450 ns. The LED therefore gives out **about 4–5 times less light** per screen update, and the flicker is no longer noticeable. Section 2.3 (sending only the bytes that changed) also helps, because fewer bits means fewer pulses.

*(Extra: an RGB LED on TIM1 PWM channels CH1N–CH3N (PB13–PB15, 1 kHz) flashes green twice on a fruit, red three times on death, and glows dim blue during pause. See `rgb_led.c`.)*

## 6. Feature 5 — Interrupts: game tick and button to pause / restart

Two interrupt sources drive the game.

### 6.1 TIM6 — the game clock (1 kHz)

TIM6 counts at 80 MHz / (79 + 1) = 1 MHz and overflows every 1000 counts, so it **interrupts every 1 ms**. The callback counts milliseconds and sets `step_pending` when the snake has to move. The interval `step_period_ms` starts at 220 ms and drops by 8 ms per fruit (minimum 80 ms), so the game speeds up. While the game is paused, the callback returns immediately, which freezes the game clock.

```c
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
  if (htim->Instance != TIM6) return;
  if (state != ST_PLAYING) return;             /* clock frozen while paused */

  if (++ms_since_step >= step_period_ms) {
    ms_since_step = 0;
    step_pending  = 1;
  }
}
```

The timer interrupt is enabled at the end of `App_Init()` with `HAL_TIM_Base_Start_IT(&htim6);`.

### 6.2 EXTI13 — button interrupt (blue USER button B1, PC13)

The button is configured with `BSP_PB_Init(BUTTON_USER, BUTTON_MODE_EXTI)` and fires an interrupt on its falling edge. It **interrupts the game at any moment**: it pauses or resumes a running game, and starts a new game from the title or game-over screen. The ISR stays very short. It only applies a 200 ms software debounce and sets a flag, and the main loop does the LCD/OLED work.

```c
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
  static uint32_t last_press_ms;
  if (GPIO_Pin != B1_Pin) return;

  const uint32_t now = HAL_GetTick();
  if (now - last_press_ms > 200) {
    last_press_ms  = now;
    button_pressed = 1;
  }
}
```

The shield's **SELECT** button (read through the ADC) triggers exactly the same action, so the player can use either button:

```c
/* SELECT (keypad) and the blue button (EXTI) do the same thing:
 * start / restart a game, or pause / resume the running one. */
static void on_select(void)
{
  switch (state) {
    case ST_PLAYING: pause_game();  break;
    case ST_PAUSED:  resume_game(); break;
    default:         start_game();  break;   /* title or game over */
  }
}
```

### 6.3 Safe data sharing between interrupts and the main loop

- Every variable written in an ISR and read in the main loop (or the reverse) is declared `volatile`, so the compiler re-reads it every time.
- The ISRs only set flags. No slow code (LCD, OLED, `printf`) runs in interrupt context.
- When the main loop changes several variables that the TIM6 ISR also reads, it briefly disables interrupts so the ISR never sees a half-updated state:

```c
static void enter_state(GameState s)
{
  __disable_irq();
  state         = s;
  ms_since_step = 0;
  step_pending  = 0;
  __enable_irq();
}
```

## 7. Conclusion

We built a complete, playable Snake game on the NUCLEO-L476RG that uses five features from the course list: the **OLED** screen for the playfield, the **LCD** for the score, the **ADC** to read five buttons from a single analog pin, the board **LED** to signal game events, and **interrupts** (timer and external) to pace the game and to pause or restart it.

The hardest part was not the game logic but the **hardware integration**. Three pins are shared between the OLED, the LCD and the LED, which forced us to:
- generate the SPI signal in software, so the clock idle level can drive LD2, with clock pulses kept as short as the OLED allows so LD2 does not flicker during screen updates;
- split every OLED transfer into exactly two bursts and send the LCD a harmless "guard" command on the shared E/D-C wire;
- send only the changed parts of the screen, to keep the transfers short.

We also learned to design with interrupts properly (short ISRs, flags, `volatile`, critical sections), to calibrate an analog input against real measurements instead of theory, and to keep everything non-blocking so the game stays responsive.

Possible improvements: read the keypad with ADC + DMA or the ADC analog watchdog interrupt instead of polling, use the MEMS accelerometer to steer the snake, and save the best score in flash memory.
